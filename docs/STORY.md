# The story

> Every voyage, every navigator, one chart.

## Dead reckoning

Without instruments, a ship's position is *reckoned* from the last known fix plus guesses about speed, heading and time. Errors pile up silently, and by the time the coast appears you may be miles off.

Working across many projects with several AI tools is the same. Each session starts by reckoning: *where was I, what changed, who touched this last?* No tool remembers the previous one's watch. Projects drift, side work goes uncharted, and finished voyages never make port.

**Waypoint** replaces reckoning with a **fix**. Every navigator writes to one ship's log, and one chart shows where every voyage stands, who last had the helm, and the next waypoint.

## Glossary

The story lives in the README, release notes, the demo, docs prose, CLI output and MCP tool descriptions. The contract (spec, rules, field names, file paths, Status values) and the dashboard's UI labels stay in plain words, so humans and machines never have to guess. Every distinct story term is paired with its plain term on its first appearance in each thing a reader may meet on its own (a README section, one CLI command's output, one tool description).

| Story term | Plain term | Meaning |
|---|---|---|
| **Voyage** | project | One folder of work, one file in `projects/` |
| **Navigator** | tool | Claude Code, Codex, ChatGPT, or you |
| **Watch** | session | One working session by a navigator |
| **Ship's log** / **log entry** | log entry | `### date — tool id` plus 1–3 lines in `## Log` |
| **Logbook** | data folder | The folder holding every voyage file (ideally a private git repo) |
| **Chart** | dashboard | `DASHBOARD.md`, `dashboard.json` and `chart.html`, generated by a fix |
| **Taking a fix** | sync | `waypoint fix`: harvest the facts, redraw the chart |
| **Next waypoint** | Next | The next step in `## Now` |
| **Hazard** | attention item | An `- Attention:` line; reefs ahead |
| **Unlogged watch** | unlogged session | A Claude Code or Codex session after the day of the last log entry |
| **Underway** | active | Status `active` |
| **Coasting** | occasional | Status `occasional` |
| **At anchor** | paused | Status `paused` |
| **In port** | done | Status `done` |
| **Harbour** | archive | `projects/_archive/`, where finished voyages rest |
| **Adrift** | going stale | Idle past its threshold |
| **Uncharted waters** | untracked folders | Activity in folders that have no voyage file yet |
| **Underway this week** | velocity | Active voyages touched in the last 7 days |
| **Watch log** | pulse | Daily activity grid per navigator |
| **Beacon** | MCP server | Remote access for navigators without a local view (ChatGPT) |
| **The three hulls** | engine, logbook, playground | Code, private data, experiments: never mixed |

## Voice

- Short, calm and concrete, like a good captain's log. The metaphor frames things; it never hides meaning.
- Use story terms in the README, docs, CLI output and MCP tool descriptions. For example: *"Fix taken: 16 voyages, 14 underway this week…"*
- **Operational UI labels use plain engineering terms** (user decision, 2026-10-14): Projects, Active, Attention, Stale, Activity, Archive, System health. The dashboard is a working tool; the story belongs in the prose around it.
- Never use a story term inside a rule an agent must follow, or in the spec's grammar. Rules say "project", "tool id", "log entry", "Status: paused".
